# 🏗 Architecture Documentation

## 📖 Context
* **Goal of the Repository**: The repository is part of an application named "easy-rag" designed to facilitate media transcription and knowledge base querying. It provides business value by automating the transcription of media files and enabling efficient querying of a knowledge base using AWS services.
* **Used Services and Libraries**:
  - **AWS Services**: AWS Lambda, AWS S3, AWS Transcribe, AWS API Gateway, AWS CloudWatch, AWS IAM, AWS Secrets Manager, AWS SQS, AWS Bedrock.
  - **Third-party Services**: Pinecone for vector storage.
  - **Libraries**: `aws-sdk-s3`, `aws-sdk-transcribe`, `aws-sdk-bedrockagent`, `serde`, `serde_json`, `serde_valid`, `nanoid`, `reqwest`.

## 📖 Overview
* **Architecture Overview**: The architecture is serverless, leveraging AWS Lambda functions to handle various tasks such as media upload, transcription, and knowledge base querying. The system uses AWS S3 for storage, AWS Transcribe for transcription services, and AWS Bedrock for knowledge base management. API Gateway is used to expose HTTP endpoints for client interaction.
* **Component Interaction**: 
  - Media files are uploaded to S3, triggering a Lambda function to start a transcription job.
  - Transcription results are processed and stored in a knowledge base.
  - Users can query the knowledge base via an API Gateway endpoint, which invokes a Lambda function to retrieve and generate responses.
* **Design Patterns and Architectural Decisions**:
  - **Event-Driven Architecture**: S3 events trigger Lambda functions.
  - **Serverless Architecture**: Utilizes AWS Lambda for compute tasks.
  - **Microservices**: Each Lambda function serves a specific purpose, promoting modularity.

## 🔹 Components

| Component Name                        | Description                                                                                   |
|---------------------------------------|-----------------------------------------------------------------------------------------------|
| `create_media_upload_link_lambda`     | Generates a presigned URL for media upload and stores metadata in S3.                         |
| `start_transcription_job_lambda`      | Initiates a transcription job when a media file is uploaded to S3.                            |
| `handle_successful_transcription_lambda` | Processes transcription results, stores them in the knowledge base, and triggers ingestion.  |
| `query_knowledge_base_lambda`         | Handles queries to the knowledge base and returns generated responses.                        |
| `aws_apigatewayv2_api`                | Provides HTTP endpoints for media upload and knowledge base querying.                         |
| `aws_s3_bucket`                       | Stores media files and transcription results.                                                 |
| `aws_bedrockagent_knowledge_base`     | Manages the knowledge base for storing and retrieving transcription data.                     |

## 🔄 Data Flow

| Data Flow Step                        | Description                                                                                   |
|---------------------------------------|-----------------------------------------------------------------------------------------------|
| Media Upload                          | User uploads media via a presigned URL generated by `create_media_upload_link_lambda`.         |
| Transcription Initiation              | S3 event triggers `start_transcription_job_lambda` to start a transcription job.               |
| Transcription Processing              | `handle_successful_transcription_lambda` processes results and updates the knowledge base.    |
| Knowledge Base Query                  | User queries the knowledge base via API Gateway, invoking `query_knowledge_base_lambda`.       |

## 📝 **Codebase Evaluation**

**Objective**: Analyze the provided codebase for technical debt, focusing on dependency & coupling, code complexity, and cloud anti-patterns.

- **Dependency & Coupling**: The codebase is well-structured with clear separation of concerns. Each Lambda function is responsible for a specific task, reducing coupling.
- **Code Complexity**: The use of Rust and its libraries like `serde` and `serde_valid` helps maintain code readability and manage complexity. However, error handling could be improved by providing more descriptive error messages.
- **Cloud Anti-patterns**: 
  - **Hardcoded Secrets**: The use of AWS Secrets Manager for storing API keys is a good practice.
  - **Inefficient Scaling**: The serverless architecture inherently supports scaling, but monitoring and adjusting Lambda memory and timeout settings could optimize performance.
  - **Improper Error Handling**: Ensure all potential errors are logged and handled gracefully, especially in network calls and AWS service interactions.

**Suggestions**:
- Enhance error handling by providing more context in error messages.
- Regularly review and adjust Lambda configurations for optimal performance.
- Implement comprehensive logging to facilitate monitoring and debugging.
