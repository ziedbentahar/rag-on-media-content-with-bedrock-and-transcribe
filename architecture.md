# 🏗 Architecture Documentation

## 📖 Context
* **Goal of the Repository**: The repository is part of an application designed to facilitate media transcription and knowledge base querying. It provides a system for uploading media files, transcribing them, and storing the transcriptions in a knowledge base that can be queried. This application offers business value by automating the transcription process and enabling efficient retrieval of information from transcriptions.
* **Used Services and Libraries**:
  - **AWS Services**: Lambda, S3, API Gateway, CloudWatch, IAM, SQS, Secrets Manager, Transcribe, Bedrock.
  - **Third-party Services**: Pinecone for vector storage.
  - **Libraries**: `aws-sdk` for AWS service interactions, `serde` for JSON serialization/deserialization, `nanoid` for generating unique IDs, `reqwest` for HTTP requests.

## 📖 Overview
* **Architecture Overview**: The architecture is serverless, leveraging AWS Lambda functions to handle various tasks such as media upload, transcription job initiation, handling successful transcriptions, and querying the knowledge base. The system uses S3 for storage, API Gateway for HTTP API management, and CloudWatch for logging and monitoring. Transcriptions are processed and stored in a Pinecone vector database for efficient querying.
* **Component Interactions**:
  - **API Gateway**: Routes HTTP requests to appropriate Lambda functions.
  - **Lambda Functions**: Perform tasks such as creating media upload links, starting transcription jobs, handling transcription results, and querying the knowledge base.
  - **S3 Buckets**: Store media files and transcription metadata.
  - **Pinecone**: Stores vectorized transcription data for querying.
  - **Event-Driven Flows**: S3 events trigger Lambda functions to start transcription jobs.
* **Design Patterns and Architectural Decisions**:
  - **Serverless Architecture**: Utilizes AWS Lambda for scalable, event-driven processing.
  - **Event-Driven Architecture**: S3 events trigger transcription jobs.
  - **Microservices**: Each Lambda function acts as a microservice with a specific responsibility.

## 🔹 Components

| Component                              | Description                                                                                   |
|----------------------------------------|-----------------------------------------------------------------------------------------------|
| `create_media_upload_link_lambda`      | Generates presigned S3 URLs for media uploads and stores metadata.                            |
| `start_transcription_job_lambda`       | Initiates transcription jobs when new media files are uploaded to S3.                         |
| `handle_successful_transcription_lambda` | Processes completed transcriptions, stores results, and updates the knowledge base.           |
| `query_knowledge_base_lambda`          | Handles queries to the knowledge base, retrieving and generating responses.                   |
| `aws_apigatewayv2_api`                 | Manages HTTP API endpoints for interacting with the system.                                   |
| `aws_s3_bucket`                        | Stores media files and transcription metadata.                                                |
| `pinecone_index`                       | Stores vectorized transcription data for efficient querying.                                  |

## 🔄 Data Flow

| Data Flow Step                          | Description                                                                                   |
|-----------------------------------------|-----------------------------------------------------------------------------------------------|
| Media Upload                            | Users upload media files via a presigned S3 URL generated by `create_media_upload_link_lambda`.|
| Transcription Job Initiation            | S3 triggers `start_transcription_job_lambda` to start a transcription job.                     |
| Transcription Processing                | `handle_successful_transcription_lambda` processes completed transcriptions and updates the knowledge base. |
| Knowledge Base Query                    | `query_knowledge_base_lambda` handles queries, retrieving data from Pinecone and generating responses. |

## 📝 **Codebase Evaluation**

**Objective**: Analyze the provided codebase for technical debt, focusing on dependency & coupling, code complexity, and cloud anti-patterns.

- **Dependency & Coupling**: The codebase is modular, with each Lambda function encapsulating specific functionality. However, there is a potential for tight coupling between Lambda functions and AWS services, which could be mitigated by abstracting service interactions.
- **Code Complexity**: The use of Rust and its strong type system helps manage complexity. However, error handling could be improved by using more descriptive error messages and consistent error propagation.
- **Cloud Anti-patterns**: 
  - **Hardcoded Secrets**: The use of AWS Secrets Manager for storing API keys is a good practice, avoiding hardcoded secrets.
  - **Inefficient Scaling**: The serverless architecture inherently scales with demand, but monitoring and optimizing Lambda memory and timeout settings could improve performance.
  - **Improper Error Handling**: Ensure all potential errors are logged and handled gracefully, especially in network calls and AWS service interactions.

**Suggestions**:
- Consider using environment variables or configuration files to manage service-specific settings and reduce hardcoding.
- Implement a centralized error handling strategy to improve maintainability and debugging.
- Regularly review and optimize AWS resource configurations to ensure cost-effectiveness and performance.
