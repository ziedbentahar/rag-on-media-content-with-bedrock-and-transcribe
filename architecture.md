# 🏗 Architecture Documentation

## 📖 Context
* **Goal of the Repository**: The repository is part of an application named "easy-rag" designed to facilitate media transcription and knowledge base querying. It provides business value by automating the transcription of media files and enabling efficient querying of a knowledge base using AWS services.
* **Notable Code Libraries and Services**:
  - **AWS Services**: AWS Lambda, AWS S3, AWS Transcribe, AWS API Gateway, AWS CloudWatch, AWS IAM, AWS Secrets Manager, AWS SQS, AWS Bedrock.
  - **Third-party Services**: Pinecone for vector storage.
  - **Libraries**: `aws-sdk` for AWS service interactions, `serde` for JSON serialization/deserialization, `lambda_http` for handling HTTP requests in Lambda, `nanoid` for generating unique IDs.

## 📖 Overview
* **Architecture Overview**: The architecture is serverless, leveraging AWS Lambda functions to handle various tasks such as media upload, transcription job initiation, handling successful transcriptions, and querying the knowledge base. The system uses AWS S3 for storage, AWS Transcribe for transcription services, and Pinecone for vector storage.
* **Component Interactions**:
  - **API Gateway**: Acts as the entry point for HTTP requests, routing them to the appropriate Lambda functions.
  - **Lambda Functions**: Perform specific tasks such as creating media upload links, starting transcription jobs, handling transcription results, and querying the knowledge base.
  - **S3 Buckets**: Store media files, transcription results, and metadata.
  - **Event-Driven Flows**: S3 events trigger Lambda functions to start transcription jobs.
  - **Design Patterns**: Event-driven architecture, serverless computing.

## 🔹 Components
| Component                              | Description                                                                                     |
|----------------------------------------|-------------------------------------------------------------------------------------------------|
| `create_media_upload_link_lambda`      | Generates presigned URLs for media uploads and stores metadata in S3.                           |
| `start_transcription_job_lambda`       | Initiates transcription jobs when new media files are uploaded to S3.                           |
| `handle_successful_transcription_lambda` | Processes completed transcription jobs, stores results in S3, and updates the knowledge base.   |
| `query_knowledge_base_lambda`          | Handles queries to the knowledge base, retrieving and generating responses using Bedrock.       |
| `AWS API Gateway`                      | Routes HTTP requests to the appropriate Lambda functions.                                       |
| `AWS S3 Buckets`                       | Stores media files, transcription results, and metadata.                                        |
| `AWS Transcribe`                       | Provides transcription services for media files.                                                |
| `Pinecone`                             | Stores vector representations of transcriptions for efficient querying.                         |

## 🔄 Data Flow
| Data Flow Step                         | Description                                                                                     |
|----------------------------------------|-------------------------------------------------------------------------------------------------|
| Media Upload                           | Users upload media files via a presigned URL generated by `create_media_upload_link_lambda`.     |
| Transcription Job Initiation           | S3 triggers `start_transcription_job_lambda` to start a transcription job for the uploaded media.|
| Transcription Completion               | `handle_successful_transcription_lambda` processes completed transcriptions and updates S3 and Pinecone. |
| Knowledge Base Query                   | `query_knowledge_base_lambda` handles queries, retrieves data from Pinecone, and returns results.|

## 📝 **Codebase Evaluation**
* **Dependency & Coupling**: The codebase uses AWS SDKs extensively, which is appropriate for the serverless architecture. However, the tight coupling between Lambda functions and specific AWS services could be abstracted to improve modularity.
* **Code Complexity**: The use of Rust and its async capabilities is well-suited for handling concurrent operations. However, the complexity of error handling and response building could be reduced by using helper functions or middleware.
* **Cloud Anti-patterns**: 
  - **Hardcoded Secrets**: The use of AWS Secrets Manager mitigates the risk of hardcoded secrets.
  - **Inefficient Scaling**: The serverless architecture inherently scales with demand, but monitoring and optimizing Lambda memory and timeout settings could improve performance.
  - **Improper Error Handling**: Ensure comprehensive error handling, especially in network calls and AWS service interactions.

**Actionable Suggestions**:
- Consider abstracting AWS service interactions into separate modules to reduce coupling.
- Implement middleware for common tasks such as error handling and response formatting.
- Regularly review and optimize Lambda configurations for performance and cost efficiency.
