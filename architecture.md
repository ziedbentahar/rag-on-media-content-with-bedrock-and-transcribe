# 🏗 Architecture Documentation

## 📖 Context
* **Goal of the Repository**: The repository is part of an application named "easy-rag" designed to facilitate media transcription and knowledge base querying. It provides business value by automating the transcription of media files and enabling efficient querying of a knowledge base using AWS services.
* **Used Services and Libraries**:
  - **AWS Services**: AWS Lambda, AWS S3, AWS Transcribe, AWS API Gateway, AWS CloudWatch, AWS IAM, AWS Secrets Manager, AWS SQS, AWS Bedrock.
  - **Third-party Libraries**: Pinecone for vector storage, `serde_json` for JSON serialization/deserialization, `nanoid` for generating unique IDs, `reqwest` for HTTP requests.

## 📖 Overview
* **Architecture Overview**: The architecture is serverless, leveraging AWS Lambda functions to handle various tasks such as media upload, transcription, and knowledge base querying. The system uses AWS S3 for storage, AWS Transcribe for transcription services, and AWS Bedrock for knowledge base management.
* **Component Interaction**:
  - Media files are uploaded to S3, triggering a Lambda function to start a transcription job.
  - Transcription results are processed and stored in a knowledge base.
  - An API Gateway facilitates interaction with the system, allowing users to query the knowledge base.
* **Design Patterns and Architectural Decisions**:
  - **Event-Driven Architecture**: Utilizes AWS S3 events to trigger Lambda functions.
  - **Serverless Architecture**: Employs AWS Lambda for scalable, on-demand execution.
  - **Microservices**: Each Lambda function acts as a microservice with a specific responsibility.

## 🔹 Components
| Component                              | Description                                                                                     |
|----------------------------------------|-------------------------------------------------------------------------------------------------|
| `create_media_upload_link_lambda`      | Generates a presigned URL for media upload and stores metadata in S3.                           |
| `start_transcription_job_lambda`       | Initiates a transcription job when a new media file is uploaded to S3.                          |
| `handle_successful_transcription_lambda` | Processes transcription results, stores them in the knowledge base, and triggers ingestion.     |
| `query_knowledge_base_lambda`          | Handles API requests to query the knowledge base and returns results.                           |
| `aws_apigatewayv2_api`                 | Provides HTTP endpoints for interacting with the system.                                        |
| `aws_s3_bucket`                        | Stores media files and transcription results.                                                   |
| `aws_bedrockagent_knowledge_base`      | Manages the knowledge base for storing and retrieving transcription data.                       |

## 🔄 Data Flow
| Data Flow Step                         | Description                                                                                     |
|----------------------------------------|-------------------------------------------------------------------------------------------------|
| Media Upload                           | User uploads media via a presigned URL generated by `create_media_upload_link_lambda`.          |
| Transcription Initiation               | S3 event triggers `start_transcription_job_lambda` to start a transcription job.                |
| Transcription Processing               | `handle_successful_transcription_lambda` processes the transcription result and updates the knowledge base. |
| Knowledge Base Query                   | `query_knowledge_base_lambda` processes user queries and retrieves relevant data from the knowledge base. |

## 📝 **Codebase Evaluation**
* **Dependency & Coupling**: The codebase effectively uses AWS SDKs and third-party libraries, maintaining a modular structure with each Lambda function handling a specific task. However, there is a potential for tight coupling between Lambda functions and AWS services, which could be mitigated by abstracting service interactions.
* **Code Complexity**: The code is well-structured with clear separation of concerns. However, error handling could be improved by providing more detailed error messages and handling edge cases.
* **Cloud Anti-patterns**: No hardcoded secrets are present, as AWS Secrets Manager is used for managing sensitive information. The use of serverless architecture ensures efficient scaling. However, the system could benefit from implementing more robust logging and monitoring to handle potential failures.

**Actionable Suggestions**:
- Consider abstracting AWS service interactions to reduce coupling and improve testability.
- Enhance error handling by providing more informative error messages and handling edge cases.
- Implement comprehensive logging and monitoring to improve system reliability and troubleshooting.
