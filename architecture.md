# 🏗 Architecture Documentation

## 📖 Context
* **Goal of the Repository**: The repository is designed to facilitate a media processing pipeline that involves uploading media files, transcribing them, and storing the transcriptions in a knowledge base. This system is likely part of a larger application aimed at managing and querying media content, providing business value by automating the transcription process and enabling efficient retrieval of information from media files.
* **Notable Code Libraries and Services**:
  - **AWS Services**: Utilizes AWS Lambda for serverless functions, AWS S3 for storage, AWS Transcribe for transcription services, AWS API Gateway for API management, AWS CloudWatch for logging, AWS IAM for access control, AWS Secrets Manager for managing sensitive information, and AWS SQS for message queuing.
  - **Pinecone**: Used for vector storage and retrieval, indicating a focus on machine learning or AI-driven features.
  - **Bedrock**: Used for knowledge base management and integration with third-party services.

## 📖 Overview
* **Architecture Overview**: The architecture is serverless, leveraging AWS Lambda functions to handle various tasks such as starting transcription jobs, handling successful transcriptions, creating media upload links, and querying the knowledge base. The system uses AWS S3 for storing media files and transcriptions, and AWS Transcribe for converting media files into text. The transcriptions are then stored in a knowledge base managed by Bedrock, with Pinecone used for vector storage.
* **Component Interactions**:
  - **API Gateway**: Routes HTTP requests to the appropriate Lambda functions.
  - **Lambda Functions**: Perform specific tasks such as creating presigned URLs for media uploads, starting transcription jobs, handling transcription results, and querying the knowledge base.
  - **S3 Buckets**: Store media files and transcription results.
  - **Event-Driven Flows**: S3 events trigger Lambda functions to start transcription jobs, and CloudWatch events handle transcription success or failure.
* **Design Patterns and Architectural Decisions**:
  - **Serverless Architecture**: Utilizes AWS Lambda for scalable, event-driven processing.
  - **Event-Driven Architecture**: S3 and CloudWatch events trigger processing flows.
  - **Microservices**: Each Lambda function acts as a microservice with a specific responsibility.

| `create_media_upload_link_lambda`  | Generates presigned URLs for media uploads to S3.                                             |

## 🔄 Data Flow
| Data Flow Step                     | Description                                                                                   |
|------------------------------------|-----------------------------------------------------------------------------------------------|
| Media Upload                       | Users upload media files via a presigned URL generated by `create_media_upload_link_lambda`.   |
| Transcription Job Start            | S3 event triggers `start_transcription_job_lambda` to initiate transcription with AWS Transcribe. |
| Transcription Success Handling     | CloudWatch event triggers `handle_successful_transcription_lambda` to process and store results. |
| Knowledge Base Query               | API Gateway routes queries to `query_knowledge_base_lambda`, which retrieves data from Bedrock. |

## 📝 **Codebase Evaluation**
* **Dependency & Coupling**: The codebase is well-structured with clear separation of concerns across different Lambda functions. However, there is a potential for tight coupling between the Lambda functions and AWS services, which could be mitigated by abstracting service interactions.
* **Code Complexity**: The use of Rust and its async capabilities is appropriate for handling concurrent tasks. However, the complexity could be reduced by modularizing the code further, especially in the Lambda functions handling multiple responsibilities.
* **Cloud Anti-Patterns**: 
  - **Hardcoded Secrets**: The use of AWS Secrets Manager mitigates the risk of hardcoded secrets.
  - **Inefficient Scaling**: The serverless architecture inherently supports scaling, but monitoring and optimizing Lambda execution times and memory usage could improve efficiency.
  - **Improper Error Handling**: Error handling is present but could be enhanced with more granular logging and retry mechanisms.

**Actionable Suggestions**:
- Consider using environment variables or configuration files to further decouple service-specific logic.
- Refactor Lambda functions to ensure single responsibility, improving maintainability and testability.
- Implement comprehensive logging and monitoring to quickly identify and resolve issues.
