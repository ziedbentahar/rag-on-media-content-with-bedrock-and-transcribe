# 🏗 Architecture Documentation

## 📖 Context
* **Goal of the Repository**: The repository is part of an application named "easy-rag" designed to facilitate media transcription and knowledge base querying. It provides business value by automating the transcription of media files and enabling efficient querying of a knowledge base using AWS services.
* **Notable Code Libraries and Services**:
  - **AWS Services**: AWS Lambda, AWS S3, AWS Transcribe, AWS API Gateway, AWS CloudWatch, AWS IAM, AWS Secrets Manager, AWS SQS, AWS Bedrock.
  - **Third-party Services**: Pinecone for vector storage.
  - **Programming Libraries**: Rust libraries such as `aws_sdk_s3`, `aws_sdk_transcribe`, `lambda_http`, `serde_json`, `serde_valid`.

## 📖 Overview
* **Architecture Overview**: The architecture is serverless, leveraging AWS Lambda functions to handle various tasks such as media upload, transcription job initiation, handling successful transcriptions, and querying the knowledge base. The system uses AWS S3 for storage, AWS Transcribe for transcription services, and Pinecone for vector-based knowledge storage.
* **Component Interactions**:
  - **API Gateway**: Acts as the entry point for HTTP requests, routing them to the appropriate Lambda functions.
  - **Lambda Functions**: Handle specific tasks such as creating media upload links, starting transcription jobs, processing transcription results, and querying the knowledge base.
  - **S3 Buckets**: Store media files, transcription results, and metadata.
  - **Event-Driven Flows**: S3 events trigger Lambda functions to start transcription jobs.
  - **Design Patterns**: Event-driven architecture, serverless computing, and microservices.

## 🔹 Components
| Component                          | Description                                                                                     |
|------------------------------------|-------------------------------------------------------------------------------------------------|
| `create_media_upload_link_lambda`  | Generates presigned URLs for media uploads and stores metadata in S3.                           |
| `start_transcription_job_lambda`   | Initiates transcription jobs using AWS Transcribe when new media is uploaded to S3.             |
| `handle_successful_transcription_lambda` | Processes completed transcription jobs, stores results in S3, and updates the knowledge base. |
| `query_knowledge_base_lambda`      | Handles queries to the knowledge base, retrieving and generating responses using Bedrock.       |
| `AWS S3 Buckets`                   | Store media files, transcription results, and metadata.                                         |
| `AWS API Gateway`                  | Routes HTTP requests to the appropriate Lambda functions.                                       |
| `AWS CloudWatch`                   | Monitors and logs application activity.                                                         |
| `AWS Secrets Manager`              | Manages sensitive information such as API keys.                                                 |
| `Pinecone`                         | Provides vector storage for the knowledge base.                                                 |

## 🔄 Data Flow
| Data Flow Step                                      | Description                                                                                     |
|-----------------------------------------------------|-------------------------------------------------------------------------------------------------|
| Media Upload                                        | Users upload media files via a presigned URL generated by `create_media_upload_link_lambda`.     |
| Transcription Job Initiation                        | S3 triggers `start_transcription_job_lambda` to start a transcription job using AWS Transcribe.  |
| Transcription Completion                            | AWS Transcribe triggers `handle_successful_transcription_lambda` upon job completion.            |
| Knowledge Base Update                               | Transcription results are stored in S3 and ingested into the knowledge base using Bedrock.       |
| Query Handling                                      | `query_knowledge_base_lambda` processes queries and retrieves information from the knowledge base.|

## 📝 **Codebase Evaluation**
* **Dependency & Coupling**: The codebase is modular, with each Lambda function handling a specific task. However, there is a tight coupling between AWS services and the application logic, which is typical in serverless architectures.
* **Code Complexity**: The use of Rust and its libraries like `serde_json` and `aws_sdk_*` is appropriate for handling JSON and AWS interactions. The code is well-structured, but error handling could be improved for robustness.
* **Cloud Anti-patterns**: 
  - **Hardcoded Secrets**: The use of AWS Secrets Manager mitigates the risk of hardcoded secrets.
  - **Inefficient Scaling**: The serverless architecture inherently supports scaling, but monitoring and optimizing Lambda execution times and memory usage could further enhance performance.
  - **Improper Error Handling**: Error handling in Lambda functions should be more comprehensive to ensure graceful degradation and logging of failures.

**Actionable Suggestions**:
- Enhance error handling in Lambda functions to provide more detailed logs and error messages.
- Regularly review and optimize Lambda memory and timeout settings based on usage patterns.
- Consider implementing retries and fallback mechanisms for external service calls to improve resilience.
